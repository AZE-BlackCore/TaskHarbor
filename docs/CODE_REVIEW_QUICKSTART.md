# 代码审查快速入门指南

> 🚀 **5 分钟了解 TaskHarbor 代码审查流程**

---

## 📖 这是什么？

这是 TaskHarbor 项目的**代码审查机制**，用于确保代码质量、安全性和可维护性。

**适用人群：**
- ✅ 新加入的开发者
- ✅ 需要提交代码的团队成员
- ✅ 负责审查代码的 Reviewer

---

## 🎯 核心流程

### 开发者提交代码

```mermaid
graph LR
    A[本地开发] --> B[自查]

    D --> E[等待审查]

    E --> F[跟踪修改]
```

## ⚡ 快速开始

### 作为开发者（提交代码）

#### 1️⃣ 提交前自查（5 分钟）

**运行自动化检查：**

```bash
# 1. 类型检查
npm run typecheck:all

# 2. Lint 检查
npm run lint

# 3. 构建验证
npm run build:all

# 4. 运行测试
npm test
```

**快速自查清单：**

- [ ] 代码能正常运行
- [ ] 无 TypeScript 错误
- [ ] 无 ESLint 错误
- [ ] 无 console.log 等调试代码
- [ ] 敏感信息未硬编码

#### 2️⃣ 创建 Pull Request

使用 [PR 模板](../.github/PULL_REQUEST_TEMPLATE.md) 填写：

```markdown
## 📝 变更说明
[简要描述变更内容]

## 🔗 关联 Issue
Closes #123

## 🧪 测试
- [x] 已测试核心功能
- [x] 无 TypeScript 错误
- [x] 已通过 Lint 检查
```

#### 3️⃣ 等待审查

- 审查者会在 **24 小时内** 完成审查
- 关注 PR 通知和评论
- 及时回复审查意见

#### 4️⃣ 修改反馈

**对每个评论进行回复：**

- ✅ 已修复 → "已修复，请复查"
- ❓ 有疑问 → "这里我有疑问..."
- 💡 说明原因 → "这里这样设计是因为..."

#### 5️⃣ 合并代码

当所有条件满足时：
- ✅ CI 检查全部通过
- ✅ 审查者批准
- ✅ 阻塞性问题已解决

代码将被合并到主分支！

---

### 作为审查者（审查代码）

#### 1️⃣ 接收审查任务

- GitHub 通知
- 团队消息
- 审查分配

#### 2️⃣ 阅读 PR（5 分钟）

**快速浏览：**

1. PR 标题和描述
2. 变更的文件列表
3. 关联的 Issue
4. CI 检查结果

#### 3️⃣ 深入审查（15-60 分钟）

**使用 [审查清单](./CODE_REVIEW_CHECKLIST.md)**

**审查重点（按优先级）：**

🔴 **阻塞性问题（必须修复）**
- 安全性问题
- 数据完整性问题
- 关键路径错误处理

🟡 **建议性问题（应该修复）**
- 代码可维护性
- 类型安全
- 性能优化

💭 **优化建议（可选）**
- 代码风格
- 文档完善

#### 4️⃣ 写下评论

**使用 [审查评论模板](./CODE_REVIEW_TEMPLATES.md)**

**好的评论示例：**

```markdown
🔴 **阻塞：安全 - SQL 注入风险**

**位置：** `main/src/services/task.ts: 42`

**问题：** 用户输入直接拼接到 SQL 查询中。

**建议：** 使用参数化查询：
```typescript
db.run('SELECT * FROM tasks WHERE id = ?', [taskId]);
```
```

#### 5️⃣ 给出结论

**三种审查结果：**

- ✅ **批准合并** - 无阻塞性问题
- 🟡 **有条件批准** - 需修复建议性问题
- 🔴 **拒绝** - 需修复阻塞性问题

### 快速参考

#### 常见问题

**Q: 如何判断问题是阻塞性还是建议性？**

A: 问自己：**如果这个问题不修复，代码能安全上线吗？**
- 不能 → 🔴 阻塞性
- 能，但有风险 → 🟡 建议性
- 纯粹优化 → 💭 优化建议

**Q: 审查需要多长时间？**

A: 根据 PR 大小：
- 小型（< 200 行）：15-30 分钟
- 中型（200-500 行）：30-60 分钟
- 大型（> 500 行）：60-90 分钟（建议拆分）

**Q: 发现太多问题怎么办？**

A: 优先处理阻塞性问题，建议性问题可以分批提出。

**Q: 如何给出建设性反馈？**

A: 遵循"三明治法则"：
1. 先表扬优点
2. 再提出改进建议
3. 最后鼓励

## 🛠️ 工具配置

### 本地开发环境

**安装依赖：**

```bash
npm install
```

**配置编辑器：**

推荐使用 VS Code，安装以下插件：
- ESLint
- Prettier
- TypeScript

**自动格式化配置：**

在 VS Code 设置中添加：

```json
{
  "editor.formatOnSave": true,
  "editor.defaultFormatter": "esbenp.prettier-vscode",
  "editor.codeActionsOnSave": {
    "source.fixAll.eslint": true
  }
}
```

### 自动化检查

**本地运行：**

```bash
# 完整 CI 检查
npm run ci

# 单独检查
npm run typecheck:all  # 类型检查
npm run lint           # Lint 检查
npm run test           # 测试
```

**自动格式化：**

```bash
# 修复 ESLint 问题
npm run lint:fix

# 格式化代码
npm run format
```

## 💡 最佳实践

### ✅ 应该做的

**开发者：**
- 提交前充分自查
- PR 描述清晰完整
- 及时回复审查意见
- 虚心接受建议

**审查者：**
- 24 小时内完成审查
- 对事不对人
- 提供具体建议
- 表扬优秀代码

### ❌ 不应该做的

**开发者：**
- ❌ 提交前不测试
- ❌ PR 描述过于简单
- ❌ 忽视审查意见
- ❌ 抵触批评

**审查者：**
- ❌ 拖延审查
- ❌ 只批评不表扬
- ❌ 过度挑剔细节
- ❌ 人身攻击
