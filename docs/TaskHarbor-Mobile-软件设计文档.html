TaskHarbor Mobile 与双端数据同步系统

把 TaskHarbor 桌面端（Electron 28 + sql.js 本地库）延伸到 Android 手机：复用同一份数据 schema 与业务内核，由 Capacitor 8 打包可安装 APK，通过「局域网直连 + 单人自用」的同步链路实现双端数据合流。阶段一无需公网服务器，架构上预留自建同步服务的接入位。

版本 v0.1（草案） 日期 2026-10-27 状态 起草待评审 技术栈 Capacitor 8 + React 18 + Vite 5 + 原生 SQLite 基线 桌面端 v1.6.0

01项目概述

1.1背景与问题

TaskHarbor 桌面端当前版本 v1.6.0，是一个纯本地 Electron 桌面应用：数据 100% 落在本机 SQLite 文件 %APPDATA%\taskharbor\todolist.db（经 sql.js 读写），没有服务端、没有账号体系、没有任何出口到设备的网络通道——唯一的 HTTP 面是 Agent 接入用的本地 API，绑定在 127.0.0.1:18765，回环地址本身不具备跨设备可达性。

这意味着「手机上也能用」并不是一次简单的打包，而是要把一条完整的同步链路从零建起来。经核查当前代码库（main/src/services/database.ts、main/src/server/apiServer.ts、main/src/services/database-migration.ts），存在四类必须先解决的原始阻碍：

痛点表现（源自当前代码实况）
① 移动场景断档离开工位后无法查看/推进任务与日程，回公司后靠记忆补录。桌面端的今日待办、提醒弹窗、悬浮窗全部随 PC 关机失效，任务的「时效连续性」在手机上彻底断裂。
② 现有 API 不足以承载同步本地 API 仅覆盖 tasks / schedules 两个资源的 CRUD，缺失 tags、subtasks、timelogs、task_dependencies、task_tag_relations、task_reminders；且无软删除变更通道、无增量游标、无冲突元数据，只能做全量拉取——不构成同步协议。
③ 渲染层与 Electron 强耦合renderer 的 store 直接调用 preload 暴露的 window.api.*（IPC 通道），业务逻辑与 IPC 面绑死；WebView 内没有 window.api，现有 UI 代码无法直接复用到手机。
④ 删除操作在同步链路上会「假消失」软删除字段 deletedAt 目前只迁移到了 tasks / projects / subtasks 三张表；tags、schedules、timelogs 等表的删除仍是物理 DELETE，对端永远收不到「这条被删了」这条信息。
关键判断：真正的难点不在「打包 APK」，而在「让两端的数据能合得上」。打包只是交付形态，同步才是这个项目的技术主体，实施计划中超过 60% 的工作量应分配给数据层改造与同步链路。

1.2产品定位

离线优先、局域网自同步、可平滑升级到自建服务的 TaskHarbor 移动端伴侣。

  • 本地优先（Local-First）：所有读写先落本地 SQLite 并即时刷新 UI，网络只是后台异步合流通道。验收口径：飞行模式下 App 全部读写功能可用，无加载态阻塞。
  • 最小信任面：不强制上云。同步服务默认关闭，仅在用户主动开启配对会话期间在局域网监听；配对关系与 token 由用户显式建立与解除。不接受「默认拉起常驻服务」。验收口径：默认安装后无任何监听端口。
  • 内核共享：桌面与移动共用同一份数据 schema（DDL）、同一套 TypeScript 类型、同一个同步引擎。差异仅存在于「SQLite 驱动实现」与「UI 布局」。验收口径：core/schema 为单一真源，两端由同一份 DDL 建库。
  • 渐进增强：阶段一 LAN 直连（无需公网服务器），阶段二替换为一个自建同步服务即可上公网——上层业务代码零改动。验收口径：Transport 接口抽象稳定，两种实现通过同一套引擎测试。
不做什么：不做多人协作与权限体系；不做 iOS（本轮）；不做云端服务的完整实现（仅预留接口，不在阶段一交付）；不把桌面的多窗口/悬浮窗/鼠标穿透移植到手机；移动端首版不移植甘特图（Gantt）与统计报表。
形态决策：主推 Android APK（Capacitor 壳 + 现有 renderer 复用）；桌面端在其中扮演 Sync Hub（权威源）。备选形态「PWA + Trusted Web Activity」因离线能力依赖 WebView 存储、易被系统清理，不推荐作为长期数据载体。

类别要求量化指标 / 验收口径

2.3核心用例

用例主流程（Happy Path）备选流与异常
UC-01
首次配对		桌面开启同步 → 显示二维码 + 6 位 PIN → 手机扫码 → 输入 PIN → 校验通过 → 交换长期 token → 手机首次全量基线拉取 → 完成。扫码失败 → 支持手动输入 IP:Port；PIN 错 3 次 → 桌面端重新生成；IP 不通 → 提示检查同 WiFi / AP 隔离。
UC-02
离线速记		手机断网 → 新建任务 → 本地 SQLite 立即写入并 UI 刷新 → 同时入 Outbox 队列（state=pending）。App 被杀 → Outbox 已持久化，重启后仍可重放；连续创建 200 条 → 批量合并推送。
UC-03
回工位合流		连 WiFi → App 前台/周期任务唤醒 → 探测 Hub 可达 → 先 push Outbox → 再 pull 增量 → 更新游标 → UI 更新上次同步时间。Hub 不可达 → 静默退避，UI 显示「离线，N 条待同步」；部分推送失败 → 成功的清出队列，失败的保留并按指数退避重试。
UC-04
双端同改冲突		同一任务两端各自修改 → 后到达 Hub 的一侧写入成功 → 先到的那一版本被检出 → 写入 _sync_conflicts → UI 显示冲突标记 → 用户查看并决定采用哪一份。用户长期不处理 → 冲突记录保留 30 天后提示（不自动删除）；「删除 vs 修改」冲突按 ADR-07 处理：修改优先。
UC-05
Schema 升级		新版本 App 携带新 DDL → 本地打开 DB 时执行增量 migration → migration 在事务中完成 → 成功后标记版本号。migration 失败 → 回滚事务并保留原库快照，禁止半升级状态继续跑；提示用户导出数据后重置。

03总体架构设计

3.1架构分层

双端对等 + 中枢权威：两端各自是一套完整的「UI → Service → Repository → SQLite」本地闭环，中间由一层可替换的 Transport 连接，底部由不依赖 OS 的共享内核统一数据与同步语义。

图 3-1 总体架构分层：双端对等闭环 + 可替换 Transport + 共享内核

3.2技术选型

Capacitor 8 + 复用现有 renderer —— 复用率最高的务实路径

选型理由要点：① 现有 renderer 已是 Vite + React 18 + TypeScript + Tailwind 的技术组合，Capacitor 原生支持任意现代 Web 前端，无需更换框架即可获得 React 组件与 Tailwind 样式的直接复用；② 桌面端数据是 SQLite，@capacitor-community/sqlite 提供真原生 SQLite，DDL 可直接复用，避免二次建模；③ Capacitor 8 是当前稳定版（8.5.x），社区插件生态成熟，官方明确 Capacitor 9 仍处 next/alpha、不建议用于生产，因此锁 8；④ 对比引入 Flutter / RN 需要几乎全量重写 UI，双端逻辑极易漂移。

候选代码复用率数据层契合度构建成本移动端体验主要风险
Capacitor 8（推荐）高 UI 结构 + Tailwind + 类型可直接复用高 原生 SQLite，DDL 复用低 单仓双 build targetWebView 渲染，接近原生；重列表需虚化SQLite 插件的 SQL 解析 Bug（见 4.8）；小米后台限制（见 4.7）
React Native / Expo中 TS 类型可复用，UI 全重写中 需换成 op-sqlite / expo-sqlite中 独立工程 + 桥接高 原生组件两套代码库并存，逻辑漂移风险最高
Flutter 重写低 几乎全重写中 sqflite 需重新建模高 全新工程与技能栈高 原生性能最佳工作量成倍；与桌面端长期割裂
PWA + TWA高 几乎零改造差 落 IndexedDB 易被系统清理极低中 依赖浏览器内核离线可靠性不满足「数据载体」定位，否决
部署形态：桌面端维持 Electron-builder NSIS 安装包（appId: com.taskharbor.desktop）；移动端新增 Capacitor Android 工程（建议 appId: com.taskharbor.mobile），产出 arm64-v8a 签名 APK。工具链硬性要求：Node.js 22+、JDK 21、Android Studio Otter 2025.2.1+、Android Gradle Plugin 8.13.0、Gradle 8.14.3、compileSdk / targetSdk 36、minSdk 24。
版本对齐红线：@capacitor/core / cli / android 必须同一大版本；社区 SQLite 插件主版本必须与 Capacitor 主版本一致——Capacitor 8 必须配 @capacitor-community/sqlite@^8，混用 7.x 会在安装期报 peer 冲突并可能在运行期出现驱动异常。

3.4关键架构决策（ADR）

编号决策理由与影响
ADR-01同一份 DDL + 分别实现的 Driver，而非统一用 sql.js桌面端现用 sql.js（SQLite 编译到 WebAssembly，自身不负责持久化，靠整库导出落盘）。若在 Android 沿用 sql.js，必须自行实现周期性落盘，且丢掉了原生引擎的性能与 SQLCipher 加密能力。改为「schema 统一、driver 各异」：DDL 是同一份，桌面端仍走 sql.js（不改动现有逻辑），移动端走 @capacitor-community/sqlite 原生引擎。代价：必须认可两端 SQL 方言的细微差异并做收口（见 4.8）。收益：桌面端零迁移风险，移动端拿到可靠持久化与加密能力。
ADR-02引入 SyncTransport 抽象：LAN 与未来云端共用同一个 SyncEngine本轮先做局域网，后续大概率要上公网服务。若把 HTTP 调用写死进同步逻辑，届时等于重写。抽出 pair / pull / push / verify 四个动词作为稳定接口后，阶段二只需新增一个 Transport 实现。影响面：所有上层代码依赖接口而非具体实现，禁止任何地方硬编码地址直接请求。
ADR-03桌面端作为权威 Hub，所有 updatedAt 由 Hub 时钟生成这是最容易被低估的翻车点：手机与 PC 的系统时钟可能相差数秒甚至更久，若各自用自己的时间戳做「最后写入胜出」，会导致新数据被旧数据静默覆盖。决策：任何写库动作的时间戳一律由 Hub 侧产生并回传给客户端，客户端本地不做 LWW 裁决。代价：纯离线期间创建的记录缺少 Hub 时间戳，需在合流时补写。收益：彻底消除时钟漂移导致的数据丢失。
ADR-04单仓双 build target，不做 monorepo 拆分理想态是抽 packages/core 的 monorepo，但改造现有工程成本高、风险大且阻塞交付。改为在现有 renderer 内建立 src/core/（OS 无关）与 src/platform/（适配器），再增加第二套 Vite 构建入口产出移动端产物。代价：短期内桌面与移动代码仍在同一 package，需靠 lint 规则强制分层。收益：立即可落地，不阻塞；若后续确有必要升级为 monorepo，目录已是现成的切分口径。
ADR-05记录级 LWW + 冲突副本保留，不做 CRDT单人自用场景下真实并发极低，引入 CRDT / 墓碑 / 因果向量的复杂度远超收益。采用记录级最后写入胜出即可覆盖绝大多数情况；剩余情况通过「被覆盖版本写入冲突表 + UI 可见」兜底，把决策权交给人而不是算法。红线：任何情况下不允许静默丢弃数据。
ADR-06阶段一走局域网 HTTP，TLS 后置到阶段二明文 HTTP 在共享 WiFi 下存在被嗅探的理论风险（任务数据属个人隐私），但自建 CA + 证书固定会显著抬高阶段一复杂度。折中：以最小攻击面换取可达性——同步服务默认关闭、仅在配对会话内监听、只绑定 WiFi 网卡 IP、Android 网络安全策略只放行局域网网段（禁止全局明文放行）。同时把访问地址设计成 http / https 可切换，TLS 升级时 URI 层面无需返工。待办：若后续在家庭/公司公共 WiFi 高频使用，应提前启动 TLS 改造。
ADR-07「删除 vs 修改」冲突时，修改优先当一端删除、另一端修改同一条记录时有两种策略。选择「修改优先」即保留被修改的那份（记录不被删除）。理由：误删后的内容不可再生，而多余的删除意图在 UI 上重新勾一下即可。不对称的代价决定了这个选择。
ADR-08软删除必须覆盖全部同步表当前只有 tasks / projects / subtasks 三张表有 deletedAt，其余表用物理 DELETE。物理删除意味着「这条记录消失」这个事实无法同步给对端（对端会保留幽灵数据）。参与同步的表必须全部补齐软删除并改为逻辑删除。影响面：桌面端需同步调整相关查询（追加 deletedAt IS NULL），这是一次跨版本的数据层变更。

3.5备选形态

同步后端形态取舍（LAN 直连 vs 自建服务）
维度LAN 直连（阶段一 · 本轮交付）自建轻量服务（阶段二 · 预留）

结论：本轮按 LAN 直连交付；Transport 抽象的设计目标就是让「有条件了上服务器」变成一次替换而非一次重构。

04关键技术设计

4.1共享内核抽取与双 target 构建

把「与平台无关的部分」从现有 renderer 里剥离出来，让同一个仓库产出桌面端与移动端两套前端产物。

抽取与构建流程
  1. 抽取 core：将现有 renderer/src/types/index.ts 提升为 renderer/src/core/domain；新建 core/schema（DDL 单一真源）与 core/sync。此步不改 UI，只做目录移动与 import 调整，是一次可独立验证的重构。
  2. 定义 Repository 接口：按现有 IPC 面（task / tag / project / schedule / subtask / timelog / dependency / reminder）的方法签名定义接口，字段口径与现有 preload/src/index.ts 完全对齐。
  3. 桌面端 Driver 适配：实现 ElectronDriver——内部转调既有 window.api.*，把现有 store 的直接 IPC 调用替换为走 Repository。此步完成后桌面端行为必须与改造前完全一致，用现有集成测试作为回归基线。
  4. 移动端 Driver 实现：实现 CapacitorDriver——用同一份 DDL 建库，SQL 执行走原生 SQLite 插件。
  5. 双 target 构建：在现有 Vite 项目内新增移动端入口与专用构建配置，产出移动端静态产物；再由 Capacitor 复制到 Android 工程并打包。
健壮性：每一次抽取都必须保持桌面端可完整运行，不允许出现「为了移动端重构导致桌面端暂时不可用」的中间态。抽取分为多次小提交，每次提交桌面端都能通过现有 npm run typecheck:all。
约束：UI 层不得直接 import platform/*，只能依赖 core/* 的抽象；这条边界需要用 lint 规则强制，否则抽象会在两周内被绕过而失效。

4.2数据模型改造

同步能力依赖三类元数据：① 变更时间（决定先后）；② 删除标记（ADR-08）；③ 游标与队列（决定同步到哪、还有哪些没发）。现有库的 updatedAt 已存在，但删除标记覆盖不全，后两者完全没有。

机制设计参数 / 口径
软删除补齐为全部参与同步的业务表增加 deletedAt（现有 tasks / projects / subtasks 已有，需新增 tags、schedules、timelogs、task_dependencies、task_tag_relations、task_reminders），所有删除改为逻辑删除，查询一律追加 AND deletedAt IS NULL。默认 NULL；清理周期 30 天
变更来源标记增加 originDeviceId，记录最后一次修改来自哪个设备，便于排查「哪台机器改的」。UUID，安装时生成并持久化
同步元表 · _sync_state记录每张表的游标位置（上次同步到的更新时间与 ID），以及 Hub 侧的校验用摘要。每张同步表一行
同步元表 · _outbox本地写操作立即落队列，含目标表、操作类型、变更载荷、重试次数、最后错误。操作类型：upsert / delete
同步元表 · _sync_conflicts被 LWW 覆盖掉的版本在此完整留档，供 UI 展示与一键恢复。保留 30 天后提示清理
同步元表 · _sync_meta记录 schema 版本、设备 ID、Hub 配对信息、最后同步时间。schema 版本随 DDL 递增
红线：DDL 必须有单一真源。禁止在桌面端和移动端各写一份建表语句——一旦漂移，同步语义立刻失控。两端都必须由同一份 core/schema 产出。

4.3增量同步协议

四条动词覆盖全部场景：pair 建立信任、push 上传本地变更、pull 拉取对端增量、verify 全量校验兜底。

图 4-1 双向增量同步时序（push → ack → pull → ack → 冲突 → 提交）
同步端点契约
方法端点说明
GET/api/sync/meta返回 Hub 版本、schema 版本、支持的同步表清单、Hub 当前时间。作用：配对前的兼容性握手，schema 不一致时明确拒绝而非产生脏数据。
POST/api/sync/pair入：PIN；出：长期 token + Hub ID。作用：一次性凭据交换，PIN 错误三次即失效。
POST/api/sync/push入：变更数组（表、操作、主键、载荷）；出：每条的处理结果与 Hub 生成的 updatedAt。作用：客户端 → Hub。
GET/api/sync/pull入：每表游标 + 分页大小；出：增量变更集、下一页游标、服务时间。作用：Hub → 客户端。
POST/api/sync/verify入：客户端各表摘要；出：差异清单。作用：手动全量校验，用于兜底排查漂移（FR-11）。
与现有 API 的关系：桌面端现已有 127.0.0.1:18765 的 Agent 本地服务（覆盖 tasks/schedules）。同步 Hub 应作为独立服务并在独立端口运行，不去改造现有 Agent API——两者定位不同（Agent 是回环内的工具接口，Hub 是局域网内的设备接口），混在一个服务里会让「同步服务默认关闭」这条安全策略难以执行。

4.4冲突解决

单人自用场景下不做复杂算法：记录级 LWW 覆盖绝大多数情况，剩余情况「留档 + 交给人」。

冲突类型裁决策略兜底动作
双端均修改同一记录记录级 LWW：以 Hub 侧 updatedAt 较大者胜出。不做字段级合并（复杂度与收益不成比例）。被覆盖版本完整写入 _sync_conflicts，UI 显示冲突标记，支持「采用此版本」一键恢复。
一端删除 / 一端修改修改优先（ADR-07）：记录不被删除，保留修改后版本。在冲突表登记「删除意图 vs 修改内容」，由用户决定最终保留或删除。
两端均删除直接收敛为删除。无需人工介入。
外键悬挂（父记录未同步到）先同步父记录；子记录在本地暂存为「待悬挂处理」。禁止因外键失败而丢弃数据。下一轮同步自动补全；UI 提示依赖未就绪。
Schema 版本不一致握手阶段直接拒绝同步（见 4.3 的 meta 端点），不产生半同步。提示用户升级 App 或桌面端到匹配的 schema 版本。
红线：冲突不能被「自动悄悄解决掉」。任何裁决都必须留下可追溯的痕迹（要么正常出队，要么进冲突表），静默丢数据是这个系统里最严重的缺陷。

4.5设备发现与配对

二维码配网而非 mDNS 自动发现
  1. 桌面端生成二维码：内容包含本机 WiFi 网卡 IP、Hub 端口、一次性 PIN、Hub 版本。注意：PC 常有多个网卡（以太网 / WiFi / 虚拟机 / VPN），必须只取正在联网的那个 WiFi 网卡地址，并提供下拉让用户切换候选 IP。
  2. 手机扫码：解析出地址与 PIN，先请求 meta 端点握手，确认版本与可达性。
  3. PIN 确认：用户在手机确认桌面端显示的同一组 PIN（防止误扫到隔壁机器的 Hub）。
  4. 交换长期 token：配对成功后写入手机侧安全存储，之后连接无需重复配对。
为什么不用 mDNS / NSD 自动发现：一方面需要额外插件；另一方面大量家用路由器开启了「AP 隔离（客户端隔离）」，WiFi 内设备互不可见，mDNS 广播会被直接丢弃。二维码配网不依赖广播，成功率显著更高，且天然包含一次用户显式确认，安全性更好。
已知限制：路由器的 DHCP 可能给电脑分配新 IP，导致下次连接失效。应对：配对信息中保存多个候选地址并在连接失败时自动轮换；同时在 UI 提示「建议在路由器为电脑设置静态 IP / DHCP 地址保留」。

4.6Android 网络与安全策略

这是局域网方案必须实际解决的第一个硬约束：自 Android 9（API 28）起，系统默认禁止明文 HTTP 传输。若不做处理，手机访问 http://192.168.x.x:port 会被网络安全策略直接拒绝，表现为「连不上但拿不到任何有效错误」——排查成本极高。

配置项说明与要求
网络安全配置在 Android 工程中提供网络安全配置文件，仅对局域网网段放行明文。禁止使用全局 usesCleartextTraffic="true"——那会让 App 的所有流量都可能走明文，属于无谓扩大攻击面。白名单限定为家庭 / 办公私有网段。
权限声明需声明 INTERNET 与 ACCESS_NETWORK_STATE（后者用于判断网络是否计量/受限，避免在计量网络上自动同步）。
绑定地址桌面端 Hub 只绑定 WiFi 网卡 IP，不绑 0.0.0.0；避免在公共网络被同网其他人发现。
凭据存储配对 token 必须存入系统安全存储（Android Keystore 体系），不得落 localStorage / 明文 Preferences。
日志脱敏日志禁止输出任务标题、描述、备注正文；只记录 ID、表、时间戳、错误码。
TLS 升级预留：ADR-06 选择阶段一走明文 HTTP。由于访问地址已抽象为可配置项，后续切换到 HTTPS 时 URI 层无需改造，仅需增加证书信任处理（推荐采用自签证书 + 首次信任指纹的方案，避免商业证书成本）。

4.7小米（HyperOS / MIUI）机型适配

「能装上去」和「能用起来」是两件事。小米对第三方安装包的拦截与对后台进程的清理都远比原生 Android 激进，这两块必须在设计和测试用例里显式覆盖。

安装环节
  • 未知来源授权：需在系统「特殊权限 → 安装未知应用」中对相应来源放行；首次触发时系统会弹限时确认（存在读秒倒计时），需按提示完成「已知晓风险」确认。
  • 安装拦截：安全扫描可能标记为未知应用，需选择「继续安装 / 了解风险」继续；部分机型还会要求账号密码或生物识别以确认机主身份。
  • 交付建议：务必关闭系统的「安装后自动删除安装包」选项，保留 APK 以便快速重装；优先提供 arm64-v8a 包。
后台保活（决定同步能否自动发生）
  • 电池策略：应用信息中把省电策略由默认的智能限制改为「无限制」。这是最关键的一步，否则息屏数分钟后进程即被回收。
  • 自启动：需显式开启，保证进程在系统回收后能自行恢复。
  • 多任务锁定：在多任务列表中给应用加锁，防止被一键清理。
  • 通知权限：必须允许通知。前台服务的存活优先级与通知强相关，关闭通知会显著降低保活概率（同时 FR-08 的提醒也将失效）。
  • App 内引导：小米不同机型 / 版本的设置入口路径不完全一致，UI 需提供「一键前往设置」的自检清单页，逐项引导用户在正确的系统界面完成授权。
必须向用户如实呈现的限制：即使完成上述全部设置，系统的 Doze 与无线休眠仍可能把后台同步推迟到下一个系统窗口。因此本方案的同步不是硬实时，UI 必须常驻展示「上次同步时间」与「待同步条目数」，让用户始终知道数据处在什么状态——绝不能用静默失败掩盖延迟。

4.8SQL 方言约束（移动端 Driver 的硬约束）

这是一条会直接影响代码怎么写的具体约束，而非一般性建议。

已知：社区 SQLite 插件在 Android 侧会错误拆分复杂语句

该插件为了让旧版 Android 上的 SQLite 保持兼容，会在 Java 层对传入的 SQL 做文本处理。已知问题包括：

  • UPSERT 陷阱：带有冲突目标的 upsert 语句（本方案同步写库的主力写法）可能被按括号错误截断，导致执行失败。
  • CTE 被忽略：公共表表达式（WITH 子句）在部分执行路径中会被丢弃，生成无效 SQL。
  • RETURNING 支持不稳定：返回子句的处理存在缺陷。

规避策略（须写入团队编码规范）：

  1. 禁止在单条语句中使用 CTE 与 RETURNING 子句。
  2. upsert 一律拆成两条显式执行：先执行 UPDATE，受影响行数为 0 时再执行 INSERT，用人工逻辑替代数据库层的冲突处理。
  3. 所有写操作包在本地事务中，保证上述「先更新后插入」的原子性。
  4. 为每张表建立最小 SQL 用例集，在真机通过后才允许合入。
影响面提示：这条约束只在移动端 Driver 生效。由于桌面端仍走 sql.js（SQLite 真实引擎，完整支持上述语法），两端 Driver 的代码不会完全一致——这正是 ADR-01 承认并接受的成本，影响范围已被收口在 platform/driver-capacitor 内部。

5.3关键交互设计

  • 创建主路径：右下悬浮按钮 → 底部半屏表单 → 保存后立即本地落库并出现在列表（不等网络）→ 顶部出现「1 条待同步」状态。
  • 同步状态表达：标题栏右侧常驻状态点。绿＝已同步并显示时间；蓝＝同步中；橙＝离线且含待同步数。点击可展开详情（上次同步时间 / 各表待同步数 / 失败原因 / 立即重试）。
  • 批量操作：长按进入多选态，底部动作条出现操作项，执行后给出汇总结果（成功 n 条，失败 m 条及原因）。
  • 空态与失败态：空列表给出明确动作引导（而非空泛文案）；同步失败必须给出可执行修复动作（例如「检查是否连接同一 WiFi」「前往允许后台运行」「Hub 版本过低，请升级」），不允许只写「同步失败」。
  • 冲突处理：冲突条目在列表显示冲突标记，详情页提供「查看被覆盖版本 / 采用此版本 / 保留当前」三选一的明确决策入口。
  • 离线与后台：所有写操作本地即时生效；自动同步仅在 WiFi 非计量网络下触发；App 退到后台不中断已开始的同步事务（在本地事务保护下完成当前批次）。

数据漂移（双端摘要不一致）verify 端点比对摘要「检出 N 处不一致」支持以 Hub 为准一键修复；修复前后均写日志，修复前提示先导出备份

7.3日志与诊断

日志策略：本地滚动文件 + 内存环形缓冲，默认保留 7 天，用户可一键导出诊断包。脱敏规则：不得记录任务标题、描述、备注、参与者姓名等业务正文；日志中仅出现记录 ID、表名、时间戳、操作类型、错误码。诊断包含：设备型号 / 系统版本 / App 版本 / Hub 版本 / schema 版本 / 同步各阶段耗时 / 最近 N 次失败的错误码 / Outbox 积压统计（不含载荷）。红线：导出诊断包前必须在 UI 明示「将不包含任务内容」，取得用户确认。

9.1里程碑

9.2风险登记

风险影响概率 × 等级应对
SQLite 插件的 SQL 解析缺陷upsert / CTE 语句执行失败，同步写库不可用高 × 严重M2 首日即在真机做 SQL 语法探针（而非等到联调）；按 4.8 拆为先 UPDATE 后 INSERT；建立最小 SQL 用例集作为回归门禁。备选：评估其他 SQLite 方案。
小米后台限制导致同步失效后台自动同步不触发，只能手动拉高 × 中FR-13 保活自检引导为必做项；UI 如实呈现延迟而非掩盖；保留手动同步与前台触发兜底；必要时用前台服务 + 常驻通知提升优先级。
路由器 AP 隔离手机找不到桌面端，配对阶段即失败中 × 中连接失败提示明确指向该原因并提供「改用手机热点」的具体操作；FR-12 文件兜底通道保证数据始终能搬运。
内核抽取引入桌面端回归主力工具变砖，直接影响日常使用中 × 严重严格 M1 → M2 串行；每次抽取小步提交并跑现有测试；保留可回滚的分支；抽取期间不改动任何业务逻辑。
双端时钟漂移导致数据覆盖新编辑被旧版本静默覆盖，属于静默数据丢失中 × 严重ADR-03 已规定由 Hub 侧统一生成时间戳；通过强制单测覆盖「客户端时钟故意拨慢」场景验证。
DDL 双写漂移两端表结构不一致，同步语义失控中 × 严重DDL 单一真源硬约束；握手阶段校验 schema 版本，不匹配直接拒绝；在集成测试中断言两端 sqlite_master 一致。
Capacitor / 插件版本升级断链升级后构建失败或运行异常中 × 中锁定 Capacitor 8 系列；Core / CLI / Android / SQLite 插件大版本必须一致；升级前先读官方迁移指引并在分支验证。
局域网明文传输的隐私暴露公共 WiFi 下存在被嗅探的理论风险低 × 中ADR-06 的最小攻击面策略；访问地址可切换为 https；若在公共网络高频使用，提前启动自签证书 + 指纹信任的 TLS 改造。

10.2术语表

术语含义
Hub桌面端进程内运行的同步服务端，同时充当时间戳权威源（ADR-03）。
Client移动端 App 中的同步客户端，本地优先、可离线。
Transport传输通道抽象层，定义 pair / pull / push / verify 四个动词；本轮实现 LanTransport。
DriverRepository 接口的具体 SQLite 实现；桌面为 ElectronDriver，移动为 CapacitorDriver。
Outbox本地写操作的持久化待发队列，断网期间积压，恢复后自动重放。
复合游标（cursor）由「更新时间 + 记录 ID」组成的增量拉取位置标记，避免同一毫秒边界丢数据。
LWWLast-Write-Wins，最后写入胜出。本方案采用记录级而非字段级。
AP 隔离路由器的客户端隔离功能，开启后同一 WiFi 下设备互不可达，会导致局域网同步失败。
软删除以 deletedAt 字段标记删除而非物理 DELETE，使「删除」这一事实可被同步。
